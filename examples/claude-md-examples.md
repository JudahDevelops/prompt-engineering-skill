# CLAUDE.md Examples

Example CLAUDE.md files for different project types. These demonstrate the principles from `reference/claude-md-guide.md`.

---

## Example 1: TypeScript Web Application

```markdown
# TaskFlow

## Quick Start

Install: `npm install`
Dev server: `npm run dev` (port 3000, hot reload)
Build: `npm run build`
Test: `npm test`
Lint: `npm run lint`
Type check: `npx tsc --noEmit`

## Architecture

- `src/app/` — Next.js App Router pages and layouts
- `src/components/` — React components (co-located with their tests)
- `src/components/ui/` — shadcn/ui primitives (do not modify directly)
- `src/lib/` — Shared utilities, hooks, and helpers
- `src/server/` — Server-side code: API routes, database queries, auth
- `src/server/db/` — Drizzle ORM schema and migrations
- `prisma/` — Legacy Prisma schema (read-only, being migrated to Drizzle)

## Conventions

- Named exports only — no default exports except Next.js pages
- Components: PascalCase files, one component per file
- Hooks: `use` prefix, in `src/lib/hooks/`
- Server actions: `src/server/actions/`, suffix with `Action` (e.g., `createTaskAction`)
- Database: snake_case columns, camelCase in TypeScript (Drizzle handles mapping)
- Imports: external packages first, then `@/` aliases, separated by blank line
- Error handling: throw `AppError` from `src/lib/errors.ts`, never raw Error

## Common Pitfalls

- `src/components/ui/` is generated by shadcn. Customize by wrapping, not editing.
- The `user.email` field is nullable in the DB despite the TS type. Migration pending — check for null.
- `src/server/` code must never be imported from client components. Use the `server-only` package guard.
- Environment variables: use `env.ts` for validation. Never use `process.env` directly.

## Testing

Run all: `npm test`
Single file: `npm test -- src/components/TaskList.test.tsx`
Watch: `npm test -- --watch`

- Use `@testing-library/react` for component tests
- Use `msw` for API mocking — handlers in `src/test/handlers.ts`
- Database tests use the test database (see `.env.test`). Run `npm run db:test:reset` to reset.

## Git

- Branch from `main`: `feat/`, `fix/`, `chore/`
- CI runs lint, type check, and tests. All must pass.
- Squash merge to main.
```

## Example 2: Python Data Pipeline

```markdown
# DataPipe

## Quick Start

Setup: `uv sync` (installs all dependencies via uv)
Run pipeline: `python -m datapipe.main --config config/prod.yaml`
Test: `uv run pytest`
Lint: `uv run ruff check .`
Format: `uv run ruff format .`
Type check: `uv run mypy src/`

## Architecture

- `src/datapipe/` — Main package
  - `extractors/` — Data source connectors (one file per source)
  - `transformers/` — Data transformation steps (pure functions)
  - `loaders/` — Output destination writers
  - `pipeline.py` — Pipeline orchestration (DAG of steps)
  - `models.py` — Pydantic models for all data schemas
- `config/` — YAML pipeline configurations (dev, staging, prod)
- `tests/` — Mirrors src/ structure. Fixtures in `tests/conftest.py`
- `scripts/` — One-off scripts (not part of the pipeline)

## Conventions

- All data schemas defined as Pydantic models in `models.py`
- Transformers are pure functions: `def transform(input: ModelA) -> ModelB`
- No side effects in transformers — all I/O happens in extractors and loaders
- Config via YAML + Pydantic Settings. Never hardcode connection strings.
- Logging: use `structlog`. Never use `print()` or bare `logging`.
- Type hints on all function signatures. `mypy --strict` must pass.

## Common Pitfalls

- The BigQuery loader expects columns in snake_case. Transformer outputs must match.
- `extractors/salesforce.py` uses a custom retry wrapper (`utils/retry.py`) because the SF API is flaky. Do not use `tenacity` directly — use the wrapper.
- Date fields: always `datetime.date`, never strings. Parse at the extractor level.
- Tests that hit external APIs must use `@pytest.mark.integration` and are skipped in CI by default. Run with `uv run pytest -m integration`.

## Testing

All tests: `uv run pytest`
Single file: `uv run pytest tests/transformers/test_normalize.py`
With coverage: `uv run pytest --cov=datapipe --cov-report=term-missing`
Integration only: `uv run pytest -m integration` (requires credentials in `.env`)

Fixture data lives in `tests/fixtures/`. Use `load_fixture("name.json")` helper.
```

## Example 3: Monorepo

```markdown
# CloudStack

Monorepo for CloudStack platform services.

## Quick Start

Install all: `pnpm install` (from root)
Build all: `pnpm run build`
Test all: `pnpm run test`
Single package: `pnpm --filter @cloudstack/api run test`

## Architecture

- `packages/api/` — REST API (Express + TypeScript)
- `packages/web/` — Customer dashboard (Next.js)
- `packages/admin/` — Internal admin panel (Next.js)
- `packages/shared/` — Shared types, utils, and validation schemas
- `packages/db/` — Database client, migrations, seed data (Drizzle)
- `infra/` — Terraform configurations (do not modify without platform team review)
- `scripts/` — Repo-level automation scripts

## Conventions

- Shared code goes in `@cloudstack/shared`. Never duplicate logic across packages.
- Package-specific CLAUDE.md files exist in `packages/api/` and `packages/web/`. Those override this file for their scope.
- All packages use the same TypeScript config: `tsconfig.base.json` at root.
- Versions: all packages share the same version (bumped together).
- PRs that touch `infra/` require a review from the platform team (@cloudstack/platform).

## Common Pitfalls

- `pnpm install` must be run from the repo root, not from individual packages.
- The `shared` package must be built before other packages that depend on it: `pnpm --filter @cloudstack/shared run build`.
- Database migrations in `packages/db/` affect all services. Coordinate with the team before modifying.
- The `admin` package uses a different auth provider than `web`. Do not share auth code between them.

## Testing

Each package has its own test setup. From root:
- All: `pnpm run test`
- Single package: `pnpm --filter @cloudstack/api run test`
- E2E: `pnpm --filter @cloudstack/web run test:e2e` (requires running API)

## Deployment

- `main` auto-deploys to staging
- Production deploys require a release tag: `git tag v1.X.Y && git push --tags`
- Rollback: `scripts/rollback.sh v1.X.Y` (reverts to a previous release tag)
```

## What Makes These Effective

1. **Every command is copy-pasteable** — no pseudocode, no "run the test command"
2. **Architecture is a map** — tells you where to find things, not how they work internally
3. **Conventions have rationale** — "(Drizzle handles mapping)" explains why the convention exists
4. **Pitfalls are specific** — not "be careful with dates" but "Date fields: always `datetime.date`, never strings"
5. **Testing section includes single-file runs** — the most common testing action
6. **Under 80 lines each** — scannable, not overwhelming
